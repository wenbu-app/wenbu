研究日期：2026-10-05（Asia/Shanghai）。状态：**研究方案，部分已实现，发布状态见 UI / UX 验收**。现状核对基于代码 `d95e716c884f1203c6911247afe8f8113fb01432`，以及本轮中文 Agent、中文邮箱入口、英文塔罗结果与保存入口的线上检查。[截图与逐步检查](../reviews/registration-timing-2026-10-05/README.md)。

实现跟进：[UI / UX 检查与发布记录](../reviews/ui-ux-2026-10-05/README.md)。首版实现结果后的可选邀请、主动保存时验证、取消隔离与返回原结果。可见曝光按前台视窗达到 50% 记录，未增加连续一秒门槛；每标签页会话一次，关闭七天抑制。下文更细的频控、回访实验与转化目标仍是建议，尚无效果结论。

## 建议采用的方案

最适合 Wenbu 先采用的策略是：**第一次完整结果后轻提示，主动保存时验证邮箱，回访查看历史时再次说明账号价值。** 欢迎页、提问引导、出生信息填写、澄清和生成过程继续保持顺畅。注册的具体价值是保留自己的探索并在其他设备继续。

这是一项有外部研究与当前产品证据支持的设计判断，不是已通过 Wenbu 转化实验验证的“最佳转化率”。本轮没有查询生产转化数据，也不根据页面截图判断用户是否愿意注册。

| 用户所处环节                          | 引导强度与动作                                                   | 具体目的                                         |
| ------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 首页、知识手册、首次打开 Agent        | 保留导航里的登录入口；开始区一句“先免费体验，结果可随后保存”即可 | 降低开始成本                                     |
| 选话题、补充资料、澄清、等待生成      | 不主动提示注册                                                   | 让用户完成当前任务                               |
| 第一次完整结果展示完毕                | 在结果操作区加入可忽略的保存提示；不自动弹窗、不遮住结果         | 让用户把账号价值与眼前的结果联系起来             |
| 点击“免费保存到账号”                  | 打开带当前结果摘要的邮箱验证面板                                 | 完成用户已经表达的保存意图                       |
| 再次打开已有对话、进入有记录的手记    | 在未被频控抑制时提示跨设备保存；固定的保存入口始终可用           | 在回看需求发生时说明价值                         |

## 研究依据与适用边界

1. **ChatGPT 的官方说明**允许在适用地区先不建账号开始对话，再通过账号保存最近的对话。这支持“先体验、在保留成果时解释账号价值”的产品模式。地区限制和会话留存政策是其自身规则，Wenbu 不应照搬，更不能声称自己的浏览器记录一离开就消失。[OpenAI Help Center](https://help.openai.com/en/articles/9125172-the-chatgpt-home-page)
2. **Baymard 的延后注册研究**观察到，在结账开始或中途插入注册邀请会分散用户注意力，完成主任务后再邀请更顺畅。对 Wenbu 的借鉴是把邀请放在产出之后；研究对象是电商结账，不能据此声称 Wenbu 的注册率会提升某个百分比。[Baymard，2023-09-19](https://baymard.com/research-articles/delayed-account-creation)
3. **NN/g 的登录墙研究**指出，在用户还不了解价值时要求付出注册成本，会阻碍首次体验。它支持把注册与明确收益联系起来。这是通用的可用性研究，不是当前命理产品的随机实验。[NN/g，2014-03-02](https://www.nngroup.com/articles/login-walls/)

以上资料在本轮重新读取。较早的研究作为交互原则参考；竞品的具体触发次数、地区实验、转化提升均未核验，不列为结论。

## 什么才算可以提示的“结果”

触发条件必须由产品状态决定，不能让模型在每轮回答里推销注册。

- 工具页：此次真实计算或抽取成功，完整结果已渲染。塔罗不要求额外付出一次 AI 请求才可保存；排盘也不要求先获得解读。
- Agent：本轮已经结束，至少有一份成功生成且可打开的报告、排盘、牌阵或卦象；用户已进入包含该结果的阅读区域。
- 澄清问题、搜索过程、工具开始、只有引用列表、错误、取消、尚在流式生成的内容，都不触发主动邀请。
- 第一版对纯文本回答保留固定的手动保存入口，不靠字数、模型自评或对话回合数判定“已经获得价值”。以后有可靠的结果类型契约再扩大范围。
- 示范命盘可以提供普通保存入口，但不进入真实试用结果的转化队列。

“进入视窗”只是可见性代理，不等于用户已阅读或觉得有用。提示置于结果下方的自然阅读位置，不强制滚动、不抢焦点。可见曝光可采用提示区域至少一半可见、页面处于前台且连续一秒的初始约定；该约定用于统计，不是出现弹窗的倒计时。

## 三层界面的具体设计

### 1. 结果后的轻提示

Agent 在完整结果后放一行精简的保存区，与继续提问、导出并列，保留继续探索的主操作。四种工具在结果操作区采用同样语义。不要在聊天区、结果抽屉与侧栏同时展示三份提示。

建议中文：

> **留住这次探索**
>
> 保存这次对话和结果，换个设备也能接着看。
>
> **免费保存到账号**　暂时不用

建议英文：

> **Keep this conversation**
>
> Save this conversation and its results so you can return on another device.
>
> **Save to a free account**　Not now

工具页将 conversation 替换为 reading。尚未保存的结果不要显示“已在此浏览器保存”；只有本机写入成功才显示该状态。游客 Agent 对话已经有浏览器留存时可明确说明“目前保存在此浏览器”。不使用“马上丢失”“解锁完整答案”“注册更准确”等文案。

### 2. 用户主动保存时的邮箱验证

点击明确的账号保存动作后，按 `结果 → 邮箱 → 验证码 → 当前记录保存成功 → 回到结果` 完成。邮箱登录与注册沿用同一流程，不增加昵称、密码、出生资料或完整历史导入向导。

| 位置         | 中文                                                       | English                                                                                                |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 定向保存标题 | 保存这次探索                                               | Save this reading / Save this conversation                                                             |
| 范围说明     | 验证邮箱后，保存本次对话和其中的结果。旧记录由你选择导入。 | Verify your email to save this conversation and its results. You choose which older records to import. |
| 新邮箱说明   | 首次验证会创建免费账号。无需设置密码。                     | New to Wenbu? Verifying your email creates a free account. No password needed.                         |
| 发送验证码   | 发送验证码                                                 | Send code                                                                                              |
| 提交验证码   | 验证并保存                                                 | Verify and save                                                                                        |
| 云端回执成功 | 已保存到你的账号                                           | Saved to your account                                                                                  |
| 取消         | 继续浏览，暂不保存到账号                                   | Keep exploring without cloud save                                                                      |

新账号当前默认开启云端记录。面板应明确说明“后续对话默认同步，可在账号中关闭”，不能让用户误以为永远只上传本次记录。全部旧历史仍逐项选择；已有账号关闭了云端记录时，不得无提示地改回开启。

保存流程保持这些约束：

- 用户点保存时绑定明确的记录 ID、当前版本和来源；本次结果不重抽、不重新调用模型，不清空输入框草稿。
- 取消定向保存、切换账号或从通用导航重新登录时，清理旧保存意图；只有本次明确选择的记录可以随验证导入。
- 关闭面板或验证码失败仍可查看原结果，并保留现有浏览器副本；不因为关闭注册而删除内容。
- 邮箱验证成功、云端记录保存成功是两个状态。只有服务端确认目标记录保存后才显示成功；离线、存储超限、冲突时保留可重试或导出的内容。
- 在保存成功后显示短暂状态反馈，回到原记录和滚动位置，焦点回到可用的结果操作；不要回到已经禁用的保存按钮。
- 动效采用轻量淡入和勾选状态，不增加假进度、强制等待或长庆祝动画；尊重减少动效设置。
- 移动端按钮按内容换行，验证码可整串粘贴并使用系统自动填充，关闭入口始终可见。英文文案使用 reading / conversation 区分场景。
- 邮箱和验证码只进入现有认证流程，不进入 DeepSeek 上下文、流量事件或会话回放。

### 3. 回访时的提醒

用户再次打开自己已有的对话或有内容的手记时，账号保存的收益更容易解释：

> 这些记录目前只在此浏览器。保存到账号后，换个设备也能继续。

第一版建议：每个浏览器会话最多出现一次主动提示，滚动七天最多两次；主动关闭后七天不再提醒。Agent、工具页、手记共用频控。这里的频次是保守的初始产品决定，不是研究证明的最优数字。

用户主动点击保存或登录不受频控影响。登录后关闭注册邀请，只显示当前记录的真实同步状态。账号维护、生成未结束、当前发生错误或正在填写另一表单时，暂缓主动提示。浏览器无法保存频控状态时退回本会话内限制，不使用指纹追踪。

## 埋点与判断效果

先纠正现有标签：`registration_prompt_viewed` 是账号弹窗打开，不是结果提示曝光；保留历史含义，不直接重命名后把旧数据混入新口径。`auth_started` 是发送验证码请求发起。新事件要经过现有闭集契约、服务端校验和 Insights 标签同步更新。

| 阶段     | 建议记录                                                 | 成功依据                                             |
| -------- | -------------------------------------------------------- | ---------------------------------------------------- |
| 获得结果 | 合格结果完成、结果区域曝光分别统计                       | 前者来自服务器成功回执；后者来自前台可见事件         |
| 保存提示 | 可见曝光、点击、关闭；按记录和提示版本去重               | 客户端可见信号，不能当服务器业务事实                 |
| 邮箱验证 | 面板打开、验证码请求、提供方接收 / 拒绝 / 未知、验证成功 | 发信和身份结果来自服务端；接收请求不等于邮件入箱     |
| 注册     | 新建且已验证的账号                                       | 服务端新账号记录；老用户登录单列                     |
| 保存     | 当前记录落库确认、失败或待同步                           | 服务端记录回执；点击保存与浏览器副本不能冒充云端保存 |
| 后续价值 | 激活、D1 / D7 新的完成操作、跨实例继续                   | 沿用 `account-v2` 的成熟队列与独立口径               |

允许的提示来源采用固定枚举，例如 `first_result`、`explicit_save`、`return_history`、`header`；再按语言、产品工具、访客 / 返回用户、视窗类型展示。不要收集问题正文、出生资料、验证码、邮箱或任意标题作为分析维度。

保留现有 USERDATA 与流量统计隔离：不按邮箱或匿名流量 visitor ID 跨库拼接。浏览器事件受退出统计、DNT、GPC 和拦截影响，要显示覆盖范围，不能把两套汇总总量相除后命名为精确转化率。既有试用队列可用已签名的试用操作关联后续账号保存；未来实验分组如要延续到账号，只沿用这套独立、可测量队列，使用有限版本枚举，缺失归因保留为 unknown。

决策首先看成熟七天试用队列中“新账号并完成有效结果云端保存”的比例，再看 D1 / D7 新的完成操作。注册数与提示点击率是诊断指标。首个结果完成率、继续提问率、保存失败率、验证码失败率、提示关闭率用于检查是否伤害体验。关闭不是负面用户标签。

## 验证顺序与验收

1. **先修承接和口径。** 明确保存按钮去向，带当前记录打开账号面板，完成后返回结果；补准确的曝光与结果保存事件。
2. **上线结果后的轻提示。** 保留主动保存入口和频控；语言、工具类型使用同一套规则。上线前核对真实收件箱投递、验证码登录、当前记录落库与返回，不把邮件提供方接受请求作为验收终点。
3. **再验证时机。** 在新口径稳定且样本足够后，对可测量的匿名浏览器固定分组：A 仅明确保存入口，B 增加首次结果后的轻提示。两组认证、保存能力与额度相同。不要用先后两周的总注册数直接比较。
4. **最后考虑回访提示。** 若首次提示有价值且没有降低继续使用，再测试回访策略。暂不同时实验强弹窗、提示频率、文案和额外额度。

实验开始前用基线、最小有意义差异与预定统计方案确定样本和观察窗；至少等七天转化窗口成熟。低流量时先做有明确任务的可用性访谈和错误检查，不能看几次点击就宣布胜出。D7 使用独立的成熟队列观察，不提前纳入分母。

实现验收至少覆盖：首次澄清不提示；完整结果出现一次；关闭后跨页面不重复骚扰；游客保存不丢结果；旧账号登录不记为注册；邮箱验证成功但云端保存失败不显示已保存；验证码错误与重发可恢复；注册不重置免费用量；仅导入当前选定记录；中英文窄屏不溢出；键盘关闭后焦点可继续操作；拒绝统计仍可正常使用账号。
